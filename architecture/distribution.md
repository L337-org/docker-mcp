# Distribution channels and the release pipeline

Deep detail behind the summaries in [../AGENTS.md](../AGENTS.md).
Read this before changing `Dockerfile`, `manifest.json`, `server.json`, `claude-plugin/`, `scripts/`, or the release workflows.

## Container image (`Dockerfile`)

An additional distribution channel alongside uvx-from-git (which is unchanged). One multi-stage `Dockerfile` builds variants via build args (`INSTALL_CLI`, `INSTALL_SCOUT`, `DISABLE_DOMAINS`): `full` (docker CLI + compose + buildx + scout) and `no-scout` (sets `DOCKER_MCP_SERVER_DISABLE=scout` so the absent-plugin scout tools don't register) are **published to GHCR (and mirrored to Docker Hub when the Hub secrets are set) on each GitHub Release** - the same tags on each registry (`full` -> `:latest`/`:<version>`, `no-scout` -> `:no-scout`/`:<version>-no-scout`); `lite` (`INSTALL_CLI=0`, docker-py SDK only - CLI domains degrade via `has_plugin()`) is buildable but not published. `.github/workflows/images.yaml` builds+measures on PRs/pushes to main; the `images` job in `.github/workflows/publish.yaml` (see "Release pipeline" below) pushes multi-arch images on a GitHub Release - always to GHCR, and mirrored to Docker Hub (`gavinlucas/docker-mcp-server`, plus a `DOCKERHUB.md`->Hub-description sync - a slim container-focused readme, since the full `README.md` exceeds Hub's 25 KB cap) when the opt-in `DOCKERHUB_USER`/`DOCKERHUB_TOKEN` secrets are set (the Hub token needs `read/write/delete` scope or the description PATCH 403s); with them unset, only GHCR is pushed so a release never fails for lack of Hub credentials. Two container-aware guards live behind `_utils.in_container()` (true when `/.dockerenv` exists or `DOCKER_MCP_SERVER_IN_CONTAINER=1`, set in the image) and are **inert on the host install**:

- **Filesystem guard** (`_utils.py`): `assert_host_writable` (hooked into `stream_to_file`) refuses a host-file write (`dest_path` / `container_archive_get_to_file`) to a path that isn't a host bind mount (silent loss on `--rm`); `host_read_path` enriches the "missing file" case on reads. `_host_backed` parses `/proc/self/mountinfo`.
- **Self-termination guard** (`system.py`): `startup_preflight()` (called from `main()`) pings the default daemon, prints OS-aware socket hints to **stderr** (never stdout - that's the stdio channel) on failure, and pins the server's own container id (detected against the *self host* - the first local-transport entry, which can differ from a remote default); `guard_not_self(container, host=)` then makes the destructive container-lifecycle tools refuse to act on self, **only when the call targets the self host** (override: `DOCKER_MCP_SERVER_ALLOW_SELF_TERMINATE=1`).

## Desktop Extension (MCPB bundle)

A third distribution channel (alongside uvx/PyPI and the container images) for one-click install in Claude Desktop. The repo root carries the bundle sources: `manifest.json` (the MCPB manifest, `manifest_version` 0.4, `server.type: "uv"`), `mcpb_run.py` (the bundle entry point - `from docker_mcp import main; main()`, kept at the root so `import docker_mcp` resolves however the host's managed `uv` lays out `sys.path`), `.mcpbignore` (trims the packed bundle to source + `pyproject.toml` + `uv.lock` + `README.md`/`LICENSE` + `manifest.json`/`mcpb_run.py` + `assets/`), and `assets/icon.png` (512x512). Because it's a `uv`-type bundle, the host resolves dependencies from `pyproject.toml` at install time - there's no vendored venv, so the bundle stays ~250 KB and cross-platform. `manifest.json`'s `user_config` block renders the install-dialog fields and maps them to env: `DOCKER_MCP_SERVER_HOSTS` (the single host field - `DOCKER_HOST` is deliberately **not** exposed; the bare-value shorthand keeps the simple one-daemon case a one-liner) plus the `DOCKER_MCP_SERVER_READONLY` / `_NO_DESTRUCTIVE` / `_DISABLE` switches (the container-only `_ALLOW_SELF_TERMINATE` is deliberately **not** exposed - the bundle never runs containerized). The `manifest.json` `version` is kept in step with `pyproject.toml` (`tests/test_pyproject_pins.py` asserts it), but the `mcpb` job in `.github/workflows/publish.yaml` rewrites it from the release tag at pack time so it can't drift; that job packs the `.mcpb` with `npx @anthropic-ai/mcpb` and attaches it (plus a `.sha256` recording the bare filename, so `sha256sum -c` works on downloads) to each GitHub Release. `scripts/build-mcpb.sh` is the **developer-only** local equivalent of that pack step (packs to `dist/` with an auto-incrementing name) - for smoke-testing a bundle in Claude Desktop. It stamps a **dev version** derived from `pyproject.toml` plus the git HEAD - `<version>-dev.<short-commit>[.dirty]` (`.dirty` = uncommitted changes at pack time) - so a local bundle is never mistaken for a release in Claude Desktop's extension list and is traceable to the commit it was built from despite having no tag; the stamp is written into `manifest.json` only for the duration of the pack and restored by an `EXIT` trap, so the working tree is left unmodified. It is deliberately **not** wired into CI, which uses the workflow above. `PRIVACY.md` (a no-telemetry/no-backend statement) is referenced by the manifest's `privacy_policies` and summarized in the README. **When the manifest's tool/env surface or the bundled file set changes, update this section.**

## Claude plugin (`claude-plugin/`)

A plugin for Claude Code and Cowork, listed in Anthropic's plugin directory. It is a second front-end to the same server as the `.mcpb`, not a new artefact: `.claude-plugin/plugin.json` launches `uvx docker-mcp-server==<version>`, and its `userConfig` mirrors `manifest.json`'s `user_config` option for option, mapped to the same `DOCKER_MCP_SERVER_*` env. String options with no `.mcpb` default get an explicit `""`, which the server reads as unset (`read_env`/`env_flag` in `docker_mcp/_env.py`), matching a blank `.mcpb` field. `tests/test_claude_plugin.py` holds the folder on `main` to that: version and pins against `pyproject.toml`, settings, env mapping and listing metadata against `manifest.json`, the icon as a byte-identical copy of `assets/icon.png` (a symlink blocks submission), the disclosures in the plugin README, and no `uv.lock` committed here.

**Why `uvx`, and why a lock beside it.** The directory blocks an MCP server declared as a `.mcpb` fetched from a URL and holds a bundled one (it no longer lists MCPB servers at all), so the bundle cannot be reused. Its "locked launch" supports exactly `uvx <package>==<version>` with a `uv.lock` next to the manifest (`uv run` is "not supported by the locked launch"); with that lock the portal reports "Launcher locked", the precondition it names for the Verified badge. `claude-plugin/pyproject.toml` is the launch project the lock is generated from: it pins the release, mirrors the root's `constraint-dependencies`, and is never installed (`package = false`). **Accepted cost:** a pinned `uvx` launch is held for an Anthropic reviewer on every version even with the lock ("Runs a pinned npx or uvx package"), so each release reaches directory users only after that review; every other local-server shape is held too. **Not confirmed:** Claude Code 2.1.292 loading the plugin locally ran a plain `uvx` and did not consult the lock; the portal says the locked launch installs exactly the locked set, presumably on a directory install, which cannot be observed until the plugin is listed.

**The release branch holds only the plugin.** The lock can only be generated once the release is on PyPI, after the version bump has merged, so it never lives on `main`. After `verify` passes, `scripts/claude_plugin_release.py` builds the plugin folder from the release tag, locks it against PyPI and commits it - through a GitHub App, as a commit with **no parent holding only `claude-plugin/`** - to the **`claude-plugin-release`** branch, which the directory follows (submission plugin path `claude-plugin`). Each release force-moves the branch to its new commit, and each commit is kept by an immutable tag **`claude-plugin-v<version>`**; a commit message records the release commit it was built from. *Why parentless and plugin-only:* moving a ref so that the `.github/workflows/` files it points at change needs the App to hold the **Workflows** permission - true for a forced move, and for a fast-forward to a generated commit with any parent order, as tested - and with that permission a leaked App key could push a workflow to an unprotected branch and run it with this repository's secrets. A branch with no workflow files never needs it, so the App holds **Contents: read and write** only. Do not grant it Workflows. The directory reads only the plugin folder, so it sees the same files either way. *Rejected:* a deploy key (pushes only, so its commits would be unsigned and the signed-commit rule refuses them); generated commits stacked on `main` history (needs Workflows, as above); following `main` or a release tag directly (the lock does not exist there; there is no portal API to repoint a tag per release).

**What the release jobs check before the branch moves** (`publish.yaml`, in order, failing early): `preflight` - the plugin's pins in both files against the tag; `claude-plugin-build` - PyPI serves this release's wheel and sdist, each matching PyPI's own sha256 and byte-identical to the files the `pypi` job built (that job now keeps them as the `python-dist` artefact), the lock pins the release with those hashes and every dependency from pypi.org with sha256 hashes, the folder meets the directory's limits, `claude plugin validate --strict` passes; `claude-plugin-smoke` on Linux, macOS and Windows - the plugin installs from the lock with every hash enforced and by the manifest's own `uvx`, both report the version and register the same tools, the read-only and disabled-domain settings take effect through the plugin's env mapping, and on Linux a real `system_ping` reaches the runner's Docker daemon; `claude-plugin-publish` - the App's commit is verified, parentless and has the tested folder's exact git tree (computed locally, so byte-identical is proven, not assumed), then the branch moves, is read back (and is moved straight back to where it was if wrong), and only then is the tag created. Publishing a GitHub Release is the only human step; nothing after it waits for approval. Anthropic's directory is a second gate: with **Publish new versions automatically** off on the submission, a scanned version goes live only when published in the portal.

**The same script rehearses every pull request** (`premerge.yaml`, `Claude plugin rehearsal` jobs): `build --source local` locks against a wheel built from the checkout (the version is not on PyPI yet, so the server's own lock entry is exempt from the PyPI checks, and only that entry), then the same smoke test runs on all three OSes and `publish --dry-run` reports what publishing would do to the live branch. A build locked against a local wheel is refused by `publish`.

**Guards in the script** (`decide()`, unit-tested in `tests/test_claude_plugin_release.py`): it refuses to move the branch to a release that is not newer than the one it holds, unless asked to roll back; a re-run whose release is already tagged re-tests and publishes that tagged commit rather than a new build (re-locking later could pick up newer dependencies); a run that moved the branch but failed before tagging resumes by tagging; a re-run of the current release is a no-op.

**Repository rules this depends on.** Only the App may create or update `claude-plugin-release` or force-push it; nobody, the App included, may delete it or push unsigned commits to it; only the App may create a `claude-plugin-v*` tag, and nobody may move or delete one. That takes two branch rulesets and two tag rulesets, because a ruleset's bypass list exempts its actors from every rule in it: the creation/update/force-push ruleset and the tag-creation ruleset list the App (`Integration`, by App ID) as bypass actor; the deletion/signature ruleset and the tag update/deletion ruleset have none. All of this was exercised on throwaway names before adoption. Check with `gh api repos/L337-org/docker-mcp/rulesets` (bypass actors are visible to admins only). A repository transfer can strip bypass actors silently, so re-check them after one. The App's credentials are the `PLUGIN_RELEASE_CLIENT_ID` variable and `PLUGIN_RELEASE_APP_PRIVATE_KEY` secret (the App ID, `PLUGIN_RELEASE_APP_ID`, is what the rulesets name); with either unset the publish job reports the skip.

**Constraints found the hard way:** `actions/upload-artifact` skips hidden paths by default, and the manifest lives in `.claude-plugin/`, so every plugin artefact sets `include-hidden-files: true`. A lock against local wheels must be written from the plugin folder with `--find-links ../dist` so the source is recorded relatively and still resolves on another runner. Installing from a folder of wheels, `uvx` cannot read the package's Python requirement before choosing an interpreter and may pick an older managed Python; against PyPI it can, so only the local rehearsal passes `--python` from the plugin's `requires-python`.

**To roll back the plugin** to an earlier release: (1) dispatch the **Release** workflow with `tag` set to that release (e.g. `v2.2.7`) and **`claude_plugin_rollback`** ticked - every other channel is skipped; (2) the run fetches that release's `claude-plugin-v*` commit, proves its files hash to its tree, re-runs the smoke tests on all three OSes, and force-moves the branch to it; (3) the directory scans it as a new version - publish it in the portal. A release with no plugin tag cannot be rolled back to. Fixing forward with a new release remains the normal correction (RP.4.2).

**To rotate the App's key:** generate a new private key on the App's settings page, replace the `PLUGIN_RELEASE_APP_PRIVATE_KEY` secret with it, delete the old key there, and delete the downloaded file. The rulesets name the App, not a key, so they need no change. **If the plugin's settings, pins, release checks or folder layout change, update this section.**

## Homebrew tap (`L337-org/homebrew-tap`) - PAUSED

The infrastructure exists (`scripts/docker-mcp-server.rb.tpl`, `.github/workflows/publish-homebrew.yaml`, `L337-org/homebrew-tap`) but the **release trigger is disabled, by decision**: PyPI, the container image and the `.mcpb` already cover distribution, so the tap stays paused until there is a reason to bring it back. The workflow is `workflow_dispatch`-only.

It was first disabled for a Homebrew dylib linkage failure, and that blocker still applies to what the tap would ship. Pre-built `pydantic_core` wheels can leave too little free space in the Mach-O header for Homebrew's post-install relocation to rewrite the `@rpath` ID to a longer absolute path. Whether they do depends on the release: the version that matters is the one `uv.lock` pins through `pydantic`, because the workflow builds the wheelhouse from the lock at the release tag, not from the newest release. Measured from the headers, the free space between the end of the load commands and the first section is 48 bytes in the locked `pydantic_core` 2.46.3 cp314 macOS wheels, arm64 and x86_64, against about 133 bytes for a full absolute Cellar path, while 2.49.0 has 3,088 bytes. So the blocker lifts only when a `pydantic` bump locks a `pydantic_core` with enough room: measure the locked cp314 wheels then, and confirm with a real `brew install` (step 5 below), since a header measurement is not an install. The channel is not advertised in this repo's README, and the tap's own README documents the pause rather than offering an install command.

**`skip_clean "libexec"` in the template is a candidate workaround, not the fix, and it is unverified.** `skip_clean` affects only Homebrew's post-install *cleanup* phase (symbol stripping, `.la` pruning, permission fixing) - verified against Homebrew 6.0.17, where `skip_clean?` is read only in `cleaner.rb`. It does **not** disable the separate keg-relocation step that rewrites dylib IDs via `install_name_tool`, which is where the headerpad failure occurs. Do not read its presence as evidence the issue is closed; review has now twice caught a code comment claiming otherwise (this is a Ruby formula comment, not a Python docstring). The template also keeps `Formula[...].opt_bin` rather than the `formula_opt_bin` helper `brew style` recommends, deliberately: that helper only exists from Homebrew 6.0.3, so adopting it would fail the formula on older Homebrew for a style-only gain (labelled at the line).

To re-enable: (1) add `release: types: [published]` back to `publish-homebrew.yaml`'s `on:` block; (2) re-add the Homebrew section to this repo's README; (3) restore the tap's own README, which currently documents the pause - a release regenerates only `Formula/docker-mcp-server.rb`, never that file, so it will keep saying "paused" until edited by hand; (4) confirm the tap push still lands; (5) install from the tap with `brew install` and confirm the relocation step succeeds. Step (4) has never been exercised since the tap gained a `main` ruleset (2026-08-11) requiring signed commits and a reviewed PR: the workflow does a raw `git push` of an unsigned `github-actions[bot]` commit, which only succeeds if the identity behind `secrets.TAP_GITHUB_TOKEN` holds a ruleset bypass. The tap's ruleset does grant `OrganizationAdmin` and repo-admin bypass `always`, so an org-admin-owned PAT should pass - but that is an inference, not an observation, so watch the first run.

## MCP Registry (`server.json`)

A discovery listing in the official MCP Registry (`registry.modelcontextprotocol.io`), which stores only **metadata** pointing at the artifacts the other channels already publish - so it's not a fourth artifact, just an index entry covering all of them. `server.json` (repo root, server name `io.github.L337-org/docker-mcp-server`) declares three package types in one entry: `pypi` (`docker-mcp-server`), `oci` (the GHCR image), and `mcpb` (the release `.mcpb`). The `registry` job in `.github/workflows/publish.yaml` stamps the tag version and the published `.mcpb`'s `fileSha256` into `server.json`, authenticates via **GitHub OIDC** (`id-token: write`, no stored secret), and runs `mcp-publisher publish`. The registry verifies we own each listed package by matching a marker against `server.json`'s `name`, so three markers must stay equal to it: the `<!-- mcp-name: ... -->` comment in `README.md` (PyPI long-description), the `io.modelcontextprotocol.server.name` image label in the `images` job (OCI), and the `.mcpb` URL (must contain "mcp") + its hash (MCPB). The job runs `needs: [pypi, images, mcpb]`, so all three markers are live before it starts - its short retries only absorb registry-side read lag. **The committed version in `server.json` is nonetheless kept in step with `pyproject.toml`** (asserted by `tests/test_pyproject_pins.py::test_server_json_versions_match_pyproject`, which scans every version-shaped token rather than named fields, since the version appears in four places). Restamping at release means a stale value could never reach the registry, so this is not protecting the listing - it was left stale for exactly that reason and the stale value turned out to have a cost: at 1.9.0 against a tree at 2.2.4 it read as drift to every reader and every scheduled audit, each of which had to re-derive "not drift, just stamped at release". A recurring false positive is worse than one more line in the bump checklist. **If `server.json`'s name/markers or the package set change, update this section.**

## Release pipeline (`.github/workflows/publish.yaml`)

All publishing runs through one workflow on each **published GitHub Release** (nothing publishes without that human step): `preflight` -> `pypi` + `images`(->`dockerhub-description`) + `mcpb` -> `registry` -> `verify` -> `claude-plugin-build` -> `claude-plugin-smoke` (three OSes) -> `claude-plugin-publish`, with `skill` running in parallel from `preflight` and joining at `verify`, and a `notify` job on failure. The `skill` job is deliberately **not** in `registry`'s `needs` (the registry entry doesn't reference the skill archives) but **is** in `verify`'s and `notify`'s, or verify could race ahead of it and a pack failure would file no issue. `dockerhub-description` is in `verify`'s `needs` for the same reason. `preflight` resolves the tag once for every job (each checks out **the tag ref**, not the event SHA) and fails fast if the tag disagrees with the committed `pyproject.toml` / `manifest.json` / `uv.lock` self-entry versions, and the Claude plugin's `version` and `uvx` pin - preventing a split-brain release (PyPI ships the pyproject version; every other channel ships the tag version). It also refuses to run when `github.repository_owner` isn't `L337-org`, so a release published from a fork (or mis-timed around a repo transfer) fails before anything ships rather than half-publishing. `verify` confirms every channel actually serves the version (PyPI JSON API, the images, the `.mcpb` asset + checksum, the registry listing, and the skill archive - checksum plus an extraction asserting it really is rooted at `l337-docker/SKILL.md` and stamps this release's `VERSION`) so a partial release is loud. For the images it asserts that all four tags - pinned `:<version>`/`:<version>-no-scout` and moving `:latest`/`:no-scout` - resolve to the same digest as the GHCR pinned tag, on GHCR and on the Hub mirror when its secrets are set (unset, the mirror is skipped and the skip reported). One digest rather than four presence checks, so a missing tag, a divergent mirror and a stale moving tag all fail the same assertion. `notify` files (or comments on) a deduplicated issue labelled `ci-failure` + `wf:release` via the composite action `.github/actions/file-failure-issue` - one open issue per failure stream. Re-run a failed release via `workflow_dispatch` with the tag: every job is idempotent (`skip-existing` on PyPI, re-pushed image tags, `--clobber` on the `.mcpb` and the skill archive, duplicate-tolerant registry publish). Re-running the **current** release is a no-op, but re-running a **superseded** tag repoints `:latest` at the older build - `images` pushes the version tag and the moving tag in one call, so `verify`'s digest assertion passes - and the run is then stopped by `claude-plugin-publish`, whose script refuses to move the plugin release branch to an older release. Detecting rather than preventing is deliberate; a `preflight` guard refusing an older tag was considered and declined. A `workflow_dispatch` re-run of a tag from before the Claude plugin existed skips `preflight`'s plugin checks and says so. The skill archive is additionally **byte-reproducible** (sorted entries, zeroed ownership, normalised mtimes, `gzip -n`), so a re-run republishes an identical checksum rather than a new one. **PyPI Trusted Publishing pins the workflow *filename*** - the trusted publisher on PyPI must name `publish.yaml`; if the `pypi` job fails OIDC, that registration is missing. Version-bump checklist for a release: edit `pyproject.toml` + `manifest.json` + `server.json` (its `version`, the pypi package's `version`, and the version inside both the oci and mcpb `identifier` strings - `tests/test_pyproject_pins.py` fails until they all agree) + `claude-plugin/.claude-plugin/plugin.json` (its `version` and the `uvx` pin) + `claude-plugin/pyproject.toml` (its `version` and the dependency pin - both checked by `tests/test_claude_plugin.py` and `preflight`), run `uv lock`, merge, then publish a GitHub Release whose tag matches (`.github/release.yml` - GitHub's release-*notes* config, a different file - groups the generated notes, Dependabot PRs under "Dependencies"). `publish-homebrew.yaml` (paused, dispatch-only) stays separate. **When the pipeline's job graph, markers, or re-run semantics change, update this section.**
